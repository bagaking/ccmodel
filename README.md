# ccmodel

`ccmodel` switches Claude Code model configurations by managing files under
`~/.claude`.

It treats each `settings.<model>.json` file as a named candidate, writes the
active Claude Code config to `settings.json`, and keeps ccmodel-owned history,
backups, quota cache, and proxy exec session records under `~/.claude/ccmodel/`.
It also proxies Claude and Codex CLI launches when you want session records or
tmux-backed recovery around those tools.

## What ccmodel controls

`ccmodel` controls local Claude Code configuration files and ccmodel-owned run
metadata. It does not manage provider accounts, upstream Claude/Codex behavior,
or repository source code.

- `ccmodel list` reads model candidates from `~/.claude/settings.*.json`.
- `ccmodel current` compares the active `~/.claude/settings.json` against those
  candidates.
- `ccmodel switch <model>` copies a named candidate into
  `~/.claude/settings.json`.
- `ccmodel backup` copies the current active config into
  `~/.claude/backups/`.
- `ccmodel top` monitors quota macros declared in model candidate files.
- `ccmodel exec ...` launches Claude or Codex CLI processes and records local
  session metadata under `~/.claude/ccmodel/exec_sessions/`.

## Local file privacy

Files managed by ccmodel can contain provider configuration, API keys, quota
responses, workspace paths, command lines, tmux logs, and session summaries.
ccmodel treats those local files as private to the current OS user by default:

- sensitive directories it creates use `0700`
- active settings, backups, switch history, quota history, exec session JSON,
  tmux logs, and lock files it creates use `0600`
- tmux log files are created by ccmodel before tmux pipes output into them, so
  shell append behavior does not widen their permissions

Existing candidate files such as `settings.<model>.json` keep whatever
permissions the user or editor assigned. Because those files may also contain
credentials, keep `$HOME/.claude` and model candidate files readable only by
your user account.

## Runtime contract

`ccmodel` has a narrow filesystem contract:

- model candidates are `settings.<model>.json` files under `$HOME/.claude/`
- the active Claude Code configuration is `$HOME/.claude/settings.json`
- switching removes ccmodel-only macro fields `__cc` and `__ccmodel` before
  writing the active config
- `ccmodel switch <model>` backs up the previous active config under
  `$HOME/.claude/ccmodel/backups/`
- `ccmodel backup` writes manual backups under `$HOME/.claude/backups/`
- switch history, quota history, and proxy exec session records are stored under
  `$HOME/.claude/ccmodel/`

`list`, `current`, and `switch` do not need network access unless a candidate
file declares a quota macro. Quota macros may call the configured HTTP endpoint
when `list`, `current`, or `top` asks for quota data.

## Quick start

Install the CLI with Go:

```bash
go install github.com/bagaking/ccmodel@latest
```

Build a local checkout when you want to test the current repository state:

```bash
git clone https://github.com/bagaking/ccmodel
cd ccmodel
go build -o ccmodel
```

Create named model configs beside Claude Code's active config:

```bash
install -d -m 700 ~/.claude
cp ~/.claude/settings.json ~/.claude/settings.baseline.json
chmod 600 ~/.claude/settings.baseline.json
$EDITOR ~/.claude/settings.sonnet.json
chmod 600 ~/.claude/settings.sonnet.json
```

Switch and inspect:

```bash
ccmodel list
ccmodel current
ccmodel switch sonnet
ccmodel current --json
```

Shell completion is generated by the binary:

```zsh
eval "$(ccmodel completion zsh 2>/dev/null || true)"
```

## Safe smoke

`make quick-test` runs a smoke path against a temporary `HOME`. It does not
write your real `~/.claude`, does not need provider credentials, and verifies
that ccmodel-only macro fields are stripped during `switch`.

```bash
make quick-test
```

The smoke covers `list`, `current --json`, `switch`, active config creation,
and macro-field stripping from the current checkout via `go run .`.

## Command surface

| Command | Aliases | Boundary |
| --- | --- | --- |
| `ccmodel` | - | Runs `list` when no model argument is provided; switches when one model argument is provided. |
| `ccmodel list` | `ls` | Lists `settings.<model>.json` candidates and marks the active match. |
| `ccmodel current` | `status`, `whoami` | Shows the active config; `--json` emits machine-readable status. |
| `ccmodel switch <model>` | `ccmodel <model>` | Copies a cleaned candidate into `settings.json` and records switch history. |
| `ccmodel backup` | - | Copies the current `settings.json` into `~/.claude/backups/`. |
| `ccmodel top` | `monitor`, `watch` | Shows an interactive quota monitor for candidate configs. |
| `ccmodel exec ...` | - | Proxies Claude/Codex CLI runs with session records and optional tmux hosting. |
| `ccmodel completion` | - | Generates shell completion scripts. |

### JSON status

`ccmodel current --json` is the integration surface for status bars, editor
extensions, and scripts:

```bash
ccmodel current --json
ccmodel status --json
```

Example shape:

```json
{
  "model": "sonnet",
  "config_path": "<home>/.claude/settings.json",
  "file_size": 286,
  "last_modified": "2000-01-02T03:04:05Z",
  "is_active": true,
  "is_custom": false,
  "quota": {
    "total": 1000,
    "used": 250.5,
    "percent": 25.05
  },
  "sessions": {
    "claude_code": [
      {
        "id": "claude-session-id",
        "workspace": "<workspace>/project",
        "entry": "<first user input>",
        "start_time": "2000-01-02T03:04:05Z",
        "last_active": "2000-01-02T03:05:05Z",
        "duration_seconds": 60,
        "version": "1.0.0",
        "branch": "main",
        "origin": "claude_code"
      }
    ],
    "codex": [
      {
        "id": "codex-session-id",
        "workspace": "<workspace>/project",
        "entry": "<first user input>",
        "start_time": "2000-01-02T03:04:05Z",
        "last_active": "2000-01-02T03:09:05Z",
        "duration_seconds": 300,
        "version": "0.1.0",
        "branch": "main",
        "origin": "codex_cli_rs",
        "model": "gpt-5-codex"
      }
    ]
  }
}
```

Field names use lowercase snake_case. Optional fields are omitted when
unavailable, and quota or session collection errors are reported in `error`
without changing the top-level shape. The example uses `<home>` as a placeholder
for the user's home directory.

`sessions` is optional and is collected only for JSON output. When present, it
contains recent local session summaries from Claude Code project logs and Codex
session logs. Each source is sampled independently, currently up to three recent
entries. Session summaries are not privacy-scrubbed: they may include workspace
paths, git branches, CLI versions, model names, origins, timestamps, durations,
and the first user message as `entry`. Treat `current --json` as a local status
contract, not a redacted telemetry format.

### Proxy execution

`ccmodel exec` launches the native Claude or Codex CLI while recording run
metadata. It uses tmux by default when available and falls back to direct
execution when tmux cannot be used.

```bash
ccmodel exec run claude -- --help
ccmodel exec run codex -- --reset
ccmodel exec codex -- --reset
```

Supported targets are `claude`, `codex`, and the `code` alias for `codex`.
Override binary lookup with `CCMODEL_EXEC_CLAUDE` or `CCMODEL_EXEC_CODEX`.

Exec records live under `~/.claude/ccmodel/exec_sessions/`:

```text
exec_sessions/
├── <session-id>.json
└── logs/
    └── <session-id>.log
```

Useful exec commands:

```bash
ccmodel exec resume --dir .
ccmodel exec status
ccmodel exec status logs
ccmodel exec watch --simple
ccmodel exec attach
```

Public `ccmodel exec run ...` and legacy `ccmodel exec <target> ...` first
derive a directory-scoped tmux session name from the associated working
directory. The shape is `ccmodel-<dir>-<hash>`, where `<dir>` is the sanitized
directory basename and `<hash>` is derived from the absolute directory path.
`--dir` changes that association. `--name` changes the tmux window name, not the
tmux session name.

`CCMODEL_EXEC_TMUX_SESSION` is only a fallback for tmux launch paths that reach
the runner without an explicit session name. The public run paths already pass
the directory-derived name, so this environment variable does not rename those
sessions. If no explicit session name reaches the launcher and the environment
variable is empty, the final fallback is `ccmodel-exec`.

### Quota macros

Quota data is opt-in through `__ccmodel` or `__cc` in a candidate config. The
macro is read from `settings.<model>.json` and removed before that candidate is
copied into the active `settings.json`.

```json
{
  "model": "claude-3-5-sonnet",
  "env": {
    "CCMODEL_QUOTA_ACCOUNT": "demo-account"
  },
  "__cc": {
    "quota_test": {
      "post": {
        "url": "https://api.example.com/quota/check",
        "timeout": 3,
        "header": {
          "x-quota-account": "$env.CCMODEL_QUOTA_ACCOUNT"
        },
        "result": {
          "total": "data.quotaLimit",
          "used": "data.quotaUsed"
        }
      }
    }
  }
}
```

Quota macros support GET or POST requests, header/body/query variable expansion
from the candidate JSON, gjson result paths, custom timeouts, retries, and a
short local cache. They are best treated as local convenience probes, not as an
access-control or billing source of truth.

## Development and release gates

Local development uses Make targets around the Go toolchain:

```bash
make help
make dev
make quick-test
make test
make check
make build
make build-all
make release
```

Use this verification path before handing off changes:

```bash
make quick-test
go test ./...
make check
git diff --check
git diff --cached --check
```

`make check` runs `make test` and both staged and unstaged whitespace checks.
`make release` builds cross-platform binaries into `dist/` and prints the
`gh release create` command; it does not publish checksums by itself.

## Troubleshooting

`ccmodel list` only sees files named `settings.<model>.json` under
`~/.claude/`. A file named `settings.json` is the active config, not a candidate.

`ccmodel current` reports `custom` when the active `settings.json` does not match
any candidate after removing ccmodel macro fields. This can happen after manual
edits or after Claude Code changes the active file.

`ccmodel switch <model>` fails when `~/.claude/settings.<model>.json` does not
exist or is not valid JSON. The switch path parses JSON so it can remove
`__cc` and `__ccmodel`.

`ccmodel top` requires at least one candidate file. Quota columns show `-` when
no quota macro exists, the endpoint fails, or the macro cannot extract numeric
`total` and `used` values.

`ccmodel exec run ...` needs the target CLI on `PATH` unless
`CCMODEL_EXEC_CLAUDE` or `CCMODEL_EXEC_CODEX` points at a binary. tmux is
optional for `run`; without it, ccmodel records a direct execution session.
